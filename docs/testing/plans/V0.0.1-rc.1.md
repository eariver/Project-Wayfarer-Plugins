# V0.0.1-rc.1 Test Plan — Pre-client Release Candidate

- Release scope: `core`
- Requirement IDs: all applicable V0.0.1 requirements
- Candidate source: `6d25105f516a76cc373e5259fcef9d34de414543`
- Runtime authority: Paper 1.21.11 build 132 (`c5eb079`), Java 25,
  `mariadb:11.8`, and `redis:8-alpine`
- Concrete Waymark provider: `BLOCKED` by ADR 0006

## Automated and headless procedure

The dedicated `Pre-client Headless Runtime` workflow builds the candidate from source and runs
`clean check`, the Core shadow JAR task, and the test-only probe JAR task before creating an
ephemeral runtime. Paper, worlds, databases, logs, and JARs remain outside source history.

The headless cases are:

1. Verify the pinned Paper SHA-256 and select exactly one Core runtime JAR and one test probe JAR.
2. Start from an empty MariaDB schema, apply V001 through V003, publish `WayfarerServices`, and
   verify Audit, Item Identity, bounded database work, and worker-to-main-thread bridge behavior.
3. Exercise console health, transaction command fail-closed/usage behavior, Paper version,
   `tick query`, and a Java 25 thread dump without a Minecraft client.
4. Stop and restart Redis, observing health `DOWN` and then `UP`.
5. Stop Paper cleanly, restart against the existing schema, validate repeated startup and service
   lookup, and verify no duplicate service registration.
6. Tamper an isolated V001 Flyway checksum and verify Core fails closed at Migration.
7. Use an unreachable isolated MariaDB endpoint and verify Core fails closed at MariaDB.
8. Verify the synthetic credential sentinel is absent from every raw runtime log.

Provider success, timeout, unknown-effect, reconcile, queue rejection, shutdown timeout, and
concurrency cases remain authoritative in the automated fixture suites. They are not described as
concrete-provider Paper cases.

## Client-required procedure

Only real-player join/identity, player permission/output, client-visible responsiveness, and any
future authorized concrete Waymark provider behavior remain for the Project Owner. Execute
`V0.0.1-client-acceptance.md` only after the stacked PRs are reviewed and merged and an immutable
candidate is approved. Do not repeat headless-only infrastructure cases manually.

## Exit

The pre-client exit is `Automated/headless runtime passed` when the workflow and sanitized evidence
are commit-pinned. Client acceptance, Project placement, provider authority, Owner clearance, and
stable publication remain pending. Do not record `RC passed`, `Runtime test passed`, `CLEARED`, or
`READY` at this stage.
