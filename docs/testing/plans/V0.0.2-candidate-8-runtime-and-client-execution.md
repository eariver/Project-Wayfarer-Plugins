## 3. Absolute boundaries

The test environment must be fresh and disposable. Never use Project Wayfarer Runtime, Project
worlds, Project database, Project Redis namespace, Project configuration, Project secrets, or Project
Player data.

Allowed reuse from an older prepared Client Test environment:

- verified external dependency JAR bytes;
- sanitized configuration templates;
- approved Fixture bytes;
- a world-generation template containing no previous Player, inventory, plugin, or Wayfarer state.

Prohibited reuse:

- Candidate-1 through Candidate-7 Main/Frontier JARs;
- previous Candidate plugin data directories;
- previous MariaDB schemas or Redis keys;
- previous Player data, inventories, Ender Chests, statistics, advancements, or UUID mappings;
- previous scenario worlds containing test items or Launchpads;
- previous logs as current evidence.

Do not commit JARs, resolved credentials, raw logs, worlds, database dumps, Redis dumps, screenshots
containing sensitive data, or raw Player UUIDs.

The following remain unauthorized throughout this instruction:

- Product code/resource changes;
- Fixture or movement/balance changes;
- PR Ready transition or merge;
- tag, GitHub Release, release workflow, or stable publication;
- Project Issue #4 changes;
- `requirements_cleared=true`;
- production promotion.

A Product change after Candidate-8 fixation rejects Candidate-8 and requires a new Candidate. An
environment-only correction may retain Candidate-8 only when Product/Fixture bytes remain unchanged,
the correction is recorded, and the affected test state is recreated before rerun.

## 11. Repetition and defect policy

Use these bounded rules only:

```text
Basic motion:
  up to 3 attempts; stop after 3 consecutive unambiguous successes

Cooldown:
  at least 5 consecutive inputs

Entity rejection:
  1 representative attempt per configured category;
  repeat once only when ambiguous

Other deterministic scenarios:
  1 unambiguous execution

Unclear anomaly:
  hold conditions constant and expand only the affected scenario,
  up to 10 attempts
```

A major failure observed once remains material. Do not dilute it with later successes.

On a failure:

1. preserve the first evidence;
2. reproduce once when safe and deterministic;
3. classify `PRODUCT_DEFECT`, `ENVIRONMENT_DEFECT`, `OPERATOR_RESOURCE_BLOCK`, or
   `BALANCE_OBSERVATION`;
4. stop the affected scenario;
5. stop the entire test immediately for authority corruption, unintended debit, duplicate durable
   delivery, data loss, server crash, security/permission bypass, or cross-scenario contamination;
6. continue unaffected scenarios only when state remains trustworthy.

Do not modify Product code during this phase. A confirmed Product defect rejects Candidate-8.
